# 历史兼容：保留内容，不伪造协议状态

[English](history-compatibility.en.md)

## 先定义“不丢”

本地历史同时承担三种作用：给人看的对话、下次发给模型的输入、用于打开／分页／搜索的索引。三者可能来自不同记录，不能只检查模型是否不再报错。

保留目标包括正文、工具结果、附件引用、项目归属、原任务身份和可见历史。无法跨接口使用的受保护推理数据可能不能继续作为模型输入；必须解释这种上下文损失，而不是承诺模型仍记得一切。先在副本验证，确认用户接受范围，再处理正式历史。

## 盘点范围

检查当前与归档 JSONL、会话元数据、重复线程设置事件、模型 response_item、独立界面事件，以及所有相关 SQLite 和 WAL。按数据库结构发现相关库，不依赖只叫某个固定文件名。

共同身份方案中需检查的已知位置：

- session_meta.payload.model_provider；
- event_msg 中 type=thread_settings_applied 的 thread_settings.model_provider_id；
- 本地任务对应 SQLite threads.model_provider。

实际路径以当前版本为准。只用确认过的本地任务编号限定数据库行；不要把合并应用中的云端 Chat／Work、没有对应 rollout 的记录也改掉。不要全局替换字符串或假设只改第一行。

共同 model_provider = "openai" 需要先验证两种路线和新任务都能工作。归属统一与响应编号兼容分别统计、分别验收；前者不能解决后者的 400。

## 响应项目的判断

按语义类型检查编号前缀、长度、必需字段及引用，而非只找 item_：

| 情况 | 处置 |
| --- | --- |
| 已在目标客户端的实际续聊路径验证可重放 | 不改；不能只凭编号语法判定 |
| 普通消息／工具项目的编号不兼容 | 只有类型与引用可核实、目标编号无冲突时，按经过测试的规则映射 |
| 编号格式合法、有可重放内容，但原生预热后续传仍触发持久化查找 | 先做请求对照；只有确认可省略时，清理旧模型输入 ID 并保留内容。改成另一个合法编号不等于可恢复服务端状态 |
| rs_ 开头但过长 | 仍是异常，不能因为前缀正确就放行 |
| reasoning 只有合法 ID、没有 `content` 或 `encrypted_content`（包括空白／零宽摘要） | 仍不可重放；官方接口可能把它当作需服务器查找的持久化项目。只在 UI 来源已核实、轮次没有引用时移除模型输入副本 |
| reasoning 的受保护内容缺失 | 不能靠改名制造有效推理；说明影响，只在已验证方案中移除模型输入副本 |
| 加密推理无法验证、类型未知、引用不清楚 | 停止并定位，不截断 ID、不猜测字段 |

实测事故中 reasoning ID 长 79 字符，旧扫描只检查前缀而漏检；针对该目标协议增加了 64 字符边界测试。这个数值必须绑定目标版本和协议证据，不能当作所有接口的永恒常量。禁止把准备记录版本从旧值手改成新值来绕过新规则。

另一次复核发现，编号已经是合法的 `rs_` 也不代表可以提交：中转有时只保存编号和空白摘要，没有可重放正文。官方端会返回“需要持久化项目查找，但当前接口不支持”之类的 400。扫描必须同时看内容是否存在，不能把前缀／长度检查当成完整兼容性证明。

响应项目 ID、call_id、工具结果关联不是同一个概念。保留 call_id 与调用／结果配对，检查父响应、界面引用和编号冲突。目标服务保存的响应状态也不一定能跨供应商复用；遇到这类问题应识别并验证客户端实际的历史重放路径，而不是批量改字符串。

### 合法编号也可能无法跨服务续聊

0.162.0-alpha.17.2 的对照中，同一份旧历史直接发起新请求能成功，原生 WebSocket 预热后带 `previous_response_id` 续传却失败。已验证分页布局的修复保留正文和加密内容，将特定旧模型 `.id` 写成 `null` 并保留原字节空间；不是删除推理。细节见[故障复盘](continuation-case-study.md)。

已验证位置是 `response_item.payload.id` 与 `compacted.payload.replacement_history[*].id`，仅涵盖原生已识别且允许空 ID 的类型。不能因此修改 `call_id`、界面事件 ID、轮次引用、守护历史或本轮新生成的编号。其他布局、必需 ID 或无法解释的引用必须另验，不套用这项规则。

## 分页历史：最容易修坏的地方

已验证案例使用 thread_history_1.sqlite，但表名、格式和字段均属版本相关实现。改动前核对：

1. JSONL 的 ordinal、行起点字节位置、换行和编码；继承历史可能让本段从非零 ordinal 开始。
2. 分页索引的 next_rollout_byte_offset／next_rollout_ordinal 是否与本段边界一致。
3. 逻辑对话编号、实际存储分段编号和 history_base 是否对应。
4. thread_items 的来源、thread_turns 引用以及继承历史是否可解释。

续段可能使用形如“时间-逻辑编号_分段编号”的文件名：元数据和事件仍用逻辑编号，SQLite 却用分段编号。不能拿原段的游标验证续段，也不能仅凭文件名后缀决定身份；必须交叉核对元数据、文件名和继承边界。缺段或不一致就停止。

历史独立维护也可能已将双编号分段物化成无 `history_base` 的完整记录。2026-10-13 的补丁接纳了一个明确布局：ordinal 从零连续、全部元数据和事件归属一致、无残留继承，存储段游标及独立界面来源可核实。保留逻辑编号与存储编号，不凭缺少继承字段一律拒绝或一律放行；不顺手重写父关系，也不把“历史解依赖／删除旧聊天”塞进普通切换功能。

### 两种已验证投影路径

- **模型记录直接形成投影**：同步维护对应数据库行和轮次引用，目标仍是保留用户可见内容。若删除会损失唯一可见内容或留下引用，就不能把它当作自动安全修复。
- **独立界面事件形成投影**：核对每条界面行确实来自对应事件，逻辑对话、轮次、ID、类型和 ordinal 一致。模型 response_item 可能随后才出现；不能要求两者 ordinal 相同。只修模型副本，并验证界面行、轮次、继承与游标在前后未变。

旧分段还可能有独立的界面 Reasoning 事件，却没有相邻模型 `response_item` 的 `thread_items` 行。只有在其余界面投影来源已经全部核实、且 `thread_turns` 没有引用这个模型 ID 时，才可只移除模型副本；投影不完整时必须拒绝。

需要移除不可用模型输入时，一个经副本验证的方案是在原位置写入客户端会忽略的非模型事件，并保留原字节长度及 ordinal；这不是任意版本都能照抄的占位格式。必须用当前原生客户端证明旧内容显示正常且新事件可被索引。

空界面投影不必然是损坏，复制了父元数据的物化分支也不必然混入其他对话。核对归属、游标、轮次引用与压缩基线，再用原生副本读取和追加索引验证；只有证实的布局可接纳，不能一见空表就删记录，也不能取消所有来源检查。

不要直接删除 JSONL 行造成 ordinal 缺口。等字符数不等于等 UTF-8 字节数；替换必须能放进原空间并保留换行。旧 provider 比 openai 短时可能无法等长处理：应停止，不能右移后面的分页位置。需要重排时，只能使用已验证会重建本段、继承基线和新增事件投影的原生路径；没有此路径就不解除门禁。

若旧修复已经删短文件，不能按当前行号猜 ordinal 或在文件尾补空白来对齐游标。仅在原备份、旧清单、当前哈希、逐行差异和数据库原边界共同证明原布局时构造恢复副本；后来新增过内容或证据不足时停止。恢复失败撤回到本次操作前状态，而不是无条件套用更早的整份备份。

## 正式事务

默认要求所有 Desktop、CLI 及其他状态写入者退出：

1. 锁定修复任务，固定清单范围，检查格式和可恢复性。
2. JSONL 保存必要原内容及哈希；SQLite 用数据库自身备份能力覆盖 WAL 状态。
3. 持久记录计划、旧值、目标值、文件身份和回滚材料，再应用。
4. 普通历史可结构化重写；分页历史优先保留位置。每个 SQLite 库使用明确行范围的事务。
5. 验证 JSON、字节／序号边界、调用配对、投影来源、无关内容和数据库完整性。
6. 完成整个受管范围的兼容复查；未变范围可复用有效证据，变化范围重新验证，不能只统计本次修改项。保存绑定规则、数据与检查缓存的准备记录。

跨文件和跨数据库不是单一原子事务；异常或断电恢复见[安全与回滚](safety-and-rollback.md)。在线单任务救援不是批量迁移的通行证：内存中的旧设置还可能重新写回旧 provider。

## 一键切换与性能

内部区分只读扫描、停写准备、指定清单回滚和认证切换；用户界面可以把必要阶段串成一个按钮。准备失败时不启用目标认证；拒绝未知格式不是待“自动修复”的障碍。

快速就绪检查应绑定：

- 本地文件范围、路径、大小、修改时间和可用的稳定身份；
- 相关数据库及 WAL，不含只读访问可能改变的 SHM 协调缓存；
- 目标 provider／协议、修复规则版本或哈希；
- 已验证的客户端／历史布局版本和准备清单。

逐文件缓存与最终准备记录分开；缓存缺失或损坏、未完成事务都不能放行。增量实施与完整检查的选择、前缀哈希、界面来源复用和固定槽位小备份见[增量准备](incremental-preparation.md)。只读扫描不应生成“历史已准备”的写入凭证，强制完整检查则不复用旧文件结论。

元数据指纹是正常使用中的变更检测，不是防恶意篡改证明。需要更强保证时增加内容哈希。排除日志等无关库要依据结构；未知名称但有历史表的库仍要纳入。真正的历史变化必须失效，不能为了快而跳过。

分别记录扫描、分页证据核对、备份／修改／复查和凭据启用耗时。不要只记录开始写文件后的时间，就称之为“总切换时间”。一次实测中 PowerShell 逐字节解码数据库文本是主要瓶颈；等价的编译实现大幅提速，安全判断完全保留。

“首次之后永远很快”不成立：新中转记录、新数据库、规则或客户端变化都可能重新触发准备。新增记录可以只解析追加范围，不必总是全量；规则升级后不能复用过期的“零问题”结论。

## 完成条件

扫描零问题只是其中一项。还应确认：

- 内容与非自管字段没有意外变化，清单数目对得上，回滚副本测试成功；
- 新任务记录共同 provider；代表性旧任务仍在原项目中且内容可见；
- 在目标模式中，模型能继续实际回答；
- 新消息可以被原生索引读取，关闭再打开后仍正常；
- 未确认的登录、网络、加密上下文或版本差异被明确报告，而非隐藏。
