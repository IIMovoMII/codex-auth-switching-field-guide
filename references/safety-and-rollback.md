# 安全与回滚

[English](safety-and-rollback.en.md)

## 凭据边界

只报告认证类型、档案状态及脱敏错误；不向模型、日志或仓库输出密钥、OAuth 内容、Cookie 和签名网址。密钥通过本机遮罩输入或原生认证入口收集。

闲置凭据可使用 Windows DPAPI、macOS Keychain 或可用的 Linux 密钥环；先确认当前系统的权限和可移植性。Codex 正在使用的凭据必须保持它能读取的格式，不能自行加密后期待客户端识别。认证可能在文件、密钥环或两者中；别默认只替换 auth.json 就涵盖所有版本。

## 日常切换事务

- 确认写入者停止、没有冲突的外部管理器，锁定本次操作。
- 验证当前配置、目标凭据、历史就绪和备份空间；记录已接受的源状态。
- 保存当前刷新后的稳定凭据，暂存自管配置差异与目标认证。
- 在首次修改前落盘恢复日志；写入后重新解析并检查类型与路线。
- 任一步失败，恢复本次事务前的配置和认证；恢复失败时保留材料并进入“需要恢复”状态。
- 文件正确后只能标为“已应用，待重启验证”；新进程真实请求通过才是运行验收。

不要把多个文件替换描述为原子操作。事务日志要能区分“未写入、已写入、已验证、回滚中、回滚失败”，并处理断电时最后一次日志写入也可能不完整的情况。

## 两种事务分开恢复

历史准备发生在认证切换之前。历史已经成功准备、后续 OAuth 失败时，通常只回滚配置与认证；兼容的历史可保留，但要明确告知。若用户要求恢复修复前历史，则按指定历史清单执行独立回滚。不要在登录失败后悄悄把已验证历史改回不兼容状态。

历史的跨文件事务用持久清单协调；各 SQLite 库内部仍有独立事务。启动时发现未完成清单，应先判断每个目标是原状态、已应用状态还是未知状态，再继续或回滚。没有实现并测试断电恢复，就如实提供人工恢复入口，不宣称能自动处理所有中断。

## 回滚不能擦掉新数据

- 核对文件身份、哈希、记录位置和预期值后，才撤销清单记载的修改。
- 无后续活动的离线副本可按已验证哈希完整恢复；有新增活动时只能做已证明安全的字段／记录级撤销，否则停止。
- SQLite 以明确的行和预期值作条件回退，不拿旧整库覆盖新任务。
- 数据不再匹配时，保留清单及备份，标明冲突；不能说“回滚成功”。
- 重新执行回滚应幂等：已经恢复的不再修改，未知状态不猜。

分别测试异常抛出、磁盘写满、权限拒绝、进程中断和用户修改后的恢复。异常捕获成功不等于断电恢复已验证。

## 备份与容量

配置的人工恢复点可以只保留一份已知良好文件。历史修复的原内容、SQLite 备份和变更清单属于另一类恢复材料，可能包含完整隐私数据；即使诊断清单经过脱敏，也不能公开整份修复目录。

与用户约定保留份数或容量，并在预计不足时提前停止。固定覆盖一份失败摘要即可，不为每次只读检查生成新备份。旧历史恢复点只在事务完成、验收通过且不再被未完成事务引用后，按用户选择清理。不要为了达到容量上限删除唯一有效恢复材料。

有些清单本身会保存旧 item_json 或字段值用于回滚；应保护其目录和权限，不能一概宣传“清单不含正文”。

## 故障收尾

展示当前仍启用的模式、失败阶段、是否回滚成功、恢复材料位置和下一步，不展示秘密。不要无界重试。无法保证一致性时停止新切换，优先离线恢复；如果 Codex 无法启动，可以使用本机脚本或其他编程智能体读取脱敏结构。
