# 总体设计

[English](architecture.en.md)

## 四类状态，不是两份配置

| 状态 | 负责什么 | 不能推导什么 |
| --- | --- | --- |
| 实时配置 | 路线、模型和所有持续更新的扩展设置 | 配置正确不等于凭据有效 |
| 凭据档案 | 官方账号或 API 身份；闲置快照受本机系统保护 | 凭据存在不等于已登录成功或未过期 |
| 历史准备 | 已检查的数据范围、目标规则和恢复清单 | provider 一致不等于模型输入合法 |
| 运行验证 | 新进程加载后的真实路线、请求和历史表现 | 本地解析成功不等于网络请求成功 |

档案保存意图：标识、显示名、认证类型、接口地址、凭据引用，以及用户选定的模型／思考档位／代理策略。插件、MCP、Skills、钩子、权限和项目配置仍来自切换当时的实时文件。

原生 profiles、项目级配置、命令行参数和环境变量也可能影响最终值。不要只看用户级文件。选择一个路线配置写入者；CC Switch 等外部管理器冲突见[配置恢复](config-recovery.md)。

## 把版本变化隔离在适配层

主流程集中维护选择目标、先检查后启用、事务协调和失败处理。配置／认证格式、历史表、分页游标、响应编号和传输能力的版本判断放在独立函数或文件里；版本支持可以按已验证的行为和布局分组，不必每个版本复制一套代码。这里的“稳定”指尽量少受变化影响，认证和配置本身也可能变化。

版本变化先触发相关能力的重新核对，不能仅凭版本号拒绝所有新版本，也不能只因 SQLite 表结构没变就认定语义兼容。结合实际 Desktop 所用运行时、布局、规则及隔离副本的原生读取／追加索引验证决定是否复用现有实现；PATH 中的 CLI 版本不能替代 Desktop。已有实现通过验证后更新证据即可，真正不兼容时再修对应部分。证据不足时停止所依赖的写入；旧对话续聊是用户要求时，历史准备未知仍须阻止目标认证启用。

遇到已知结构外新增的无关字段可以保留；会影响目标记录解释、引用或恢复的未知字段才需要停止并定位。不要将“未知”统一做成删除、猜测或绕过检查。空文件、失效索引等修复属于按明确范围启动的维护，不应让普通切换顺手清理整个状态目录。

保持实现规模与需求一致：不必为分层引入插件管理器、下载更新服务或后台扫描。多账号、复杂界面和更多修复类型只有用户需要才实现。分层有助于限制改动范围，不保证升级永远只改一处；网络和供应商错误也不应自动触发历史修复。

保留源码版本和简短更新记录，写清规则变化、缓存失效原因、验证范围及未完成验收。这样能知道“这次为什么慢、为什么拒绝”，不用依赖聊天记忆。版本管理只收程序、合成测试和文档，不收真实配置、认证、目录缓存、聊天、数据库或恢复材料。

## 快速路径和检查失效

快速路径复用的是有范围的兼容结论。客户端相关行为、目标路线／协议、受检数据及其依赖、修复规则都仍匹配时，跳过聊天正文全量扫描、重复备份和没有失效理由的网络探针。菜单文案或无关日志变化不应使历史准备失效；相关行为或规则变了则不能靠保留旧版本号骗过缓存。

区分最终准备记录和逐文件检查证据：聊天有变化会使前者过期，但不一定要重新解析全部旧文件。简单实现可先完整重检；数据量构成瓶颈时，复用未变文件、核对完整旧前缀后只解析新增完整行，并核对数据库／继承依赖。重写、截短、移动等完整重查相应范围；规则、相关库结构或缓存损坏可要求重建基线。保留强制完整入口，具体路线与本机实测见[增量准备](incremental-preparation.md)。

不承诺固定几秒完成，也不以超时放行。先测启动、扫描、分页核对、备份修改及复查各阶段；比较相同数据和判断结果。慢检查有理由和进度，必要历史准备始终完成在认证切换之前。

## 共同 provider 身份

以下是已验证案例的候选结构，实施前需要在目标版本和中转上验证：

~~~toml
# 共同身份；官方 OAuth 模式不保留中转地址
model_provider = "openai"
~~~

~~~toml
# 中转模式增加顶层地址，并同时启用对应的 API 凭据
openai_base_url = "https://relay.example/v1"
~~~

不要在该结构中又定义 model_providers.openai 覆盖内置身份。若当前版本不支持这个地址覆盖，或目标接口不支持所需协议，应停下来适配，不能仅因旧案例可行就强制迁移历史。参考[官方配置文档](https://learn.chatgpt.com/docs/config-file/config-reference)，并用已安装版本做探针。

官方 OAuth 与 OpenAI 官方 API Key 是两种不同认证。官方 API 地址加 API Key 本身可以是合法状态；若成品仅支持“OAuth＋中转”两模式，应将其识别为范围外的第三种模式，而不是断言用户配置损坏。

## 实时配置合并

1. 解析当前配置，记录可检测并发变更的指纹。
2. 修改明确归切换器管理的字段；不改无关表、未知字段和用户新增内容。
3. 暂存并重新解析；保留注释和排版要靠可保真的编辑器，不能把语义重建伪称为字节不变。
4. 再次检查实时指纹，在已验证的文件替换机制下写入。
5. 检查生效配置与凭据类型；重启后验证真实请求。

不要为了省事交换整份 config.toml。遇到编辑器不支持的 TOML 语法应停止并说明，而不是覆盖为简化模板。只有明确的灾难恢复才可能用整份已知良好配置替换损坏文件。

## 上下文上限是独立的用户策略

先确认用户要沿用模型默认、按档案设置，还是两种模式保持相同上限；没有要求就不要顺手缩小或扩大。上限、自动压缩阈值、当前已占用量和思考档位不是同一设置，也不是每次请求必然按上限收费。

本机用户选择全部模型保持 272000。该实现停机后核对活动模型目录与 `models_cache.json` 的每个 `context_window`，只在不符时修正，保持模型名和思考档位；遇到不完整或无法解析的目录在启用目标认证前停止。它不是其他用户应复制的固定值，也不证明目标服务实际支持任意窗口。

新实现先核对当前版本支持的 `model_context_window`、`model_catalog_json` 及实际覆盖来源（见[官方配置文档](https://learn.chatgpt.com/docs/config-file/config-reference)），优先选择最小可验证方式。若目标 Desktop 还需目录／缓存适配，先在副本验证，只改已确认字段，并为这些文件定义自己的写前恢复和失败状态；不能假设配置／认证事务会替它们回滚。重复切换已经满足策略时不重写。

用新进程检查代表性新旧任务与各受管模型；缓存和已载入任务可能有旧值。修改上限不会自动减少已经积累的上下文，必要压缩另行判断，不能靠改历史 token 统计假装生效。运行时可能预留一部分窗口，本机 95% 后显示为 258400；这是该运行时的行为，不是第二个必须照抄的上限。逐模型、跨模式验收见[验证清单](validation.md)。

## 一键入口与高级入口

推荐的日常流程：

~~~text
选择目标 → 检查写入者和未完成事务 → 核对当前状态
         → 历史快速检查；需要时自动准备
         → 保存当前凭据的最新状态 → 切换自管配置与目标凭据
         → 本地验证 → 提示重启 → 实际使用验收
~~~

历史准备可以和切换合并为一个用户动作，但必须在启用目标认证之前完成；显示为什么需要以及耗时阶段。授权不包含历史改写时先询问，拒绝后不得承诺旧任务已兼容。

按目标决定准备范围：本机两模式案例在中转→官方时检查官方历史兼容，返回中转不重复做这项准备。其他账号／供应商若有不同要求，应另验目标规则；不要把最昂贵的单向准备无条件塞进所有切换，也不要推导任何反向切换都永远不用检查。

高级选项可保留只读诊断、定向历史恢复、重新登录和配置恢复。无需为了“功能完整”塞进大量菜单。

## 失败与中断

配置文件、认证文件和多个数据库不共享一个原子事务。用持久日志协调阶段；单个 SQLite 库再使用自身事务。恢复失败也是要呈现的状态，不得一律显示“已回滚”。

本地状态建议区分：未初始化、缺少目标凭据、准备中、已写入待重启、已实测可用、需重新登录、需恢复。OAuth 刷新后应捕获稳定的新凭据，不用长期旧快照覆盖它。详情见[首次使用](first-use-bootstrap.md)和[安全与回滚](safety-and-rollback.md)。
