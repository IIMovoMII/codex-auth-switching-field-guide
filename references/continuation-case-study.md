# 续聊故障复盘：扫描通过，为什么官方仍报错

[English](continuation-case-study.en.md)

记录于 2026-10-13；实验及停机执行发生于 2026-10-12。环境是 Windows 与 Desktop 使用的原生运行时 `0.162.0-alpha.17.2`。这是脱敏经验，不附本机修复程序、真实对话、凭据或备份。

后续更新：下文“待补强”描述事故当时的状态。2026-10-14 已加入增量准备和未完成历史事务恢复门禁，通过副本及模拟中断测试；不是实际断电或所有强杀位置的验收。后续证据见[增量准备](incremental-preparation.md)与[验证清单](validation.md)。

## 一个报错，两类缺口

切回官方后，旧任务续聊和上下文压缩出现：

~~~text
Supplied input item IDs require persisted-item lookup that is not supported by rustresponsesapi.
~~~

旧扫描已覆盖通用前缀、过长编号和没有可重放内容的推理，却仍报告零问题。这次同时发现了两个独立缺口：**实际续传的旧编号不兼容**，以及**更早的修复曾删短一个分页分段**。不是所有正文损坏，也不能把错误一概归因于缺少加密推理。

## 必须复现 Desktop 真正走的路径

同一份故障历史得到如下对照：

| 请求方式 | 观察结果 |
| --- | --- |
| 直接发起新的官方 HTTP 请求 | 成功，但不能证明 Desktop 续聊可用 |
| 直接发起新的官方 WebSocket 请求 | 成功，同样不是实际失败路径 |
| 原生先预热，再带 `previous_response_id` 与旧历史继续 | 触发上述查找错误，编号合法且保留加密内容也不够 |
| 正式代码清理已验证可省略的旧模型输入 ID，再走同一预热／续传 | 成功，正文、工具关联、加密推理与压缩内容保留；本轮新 ID 由原生客户端管理 |

只清理普通消息／工具编号而保留其他旧模型编号的对照也未通过，因此不能只修最先报错的一类项目。

[官方上下文说明](https://developers.openai.com/api/docs/guides/conversation-state)区分响应引用与完整历史重放，也说明 WebSocket 延续使用响应引用。[推理说明](https://developers.openai.com/api/docs/guides/reasoning)介绍受保护推理的重放。它们提供概念依据，不是对下述本地文件补丁的官方授权或跨版本保证。

## 已验证的写入边界

本机分页格式只处理 `response_item.payload.id` 和 `compacted.payload.replacement_history[*].id` 中原生已识别、允许空 ID 的旧模型项目。将字符串改为 `null`，余下字节以空格留在原槽位，保留行数、UTF-8 字节边界、ordinal 与换行。

保留正文、工具参数与结果、`call_id`、调用／结果配对、加密推理与压缩内容、独立界面事件、守护历史和来源元数据。不可重放推理另按已验证规则等长占位，不能借此删除所有 reasoning。旧式非分页文件不套用此次规则。

只修改模型 ID 不代表任意客户端都会接受。必需 ID、未知类型、受影响引用或无法核实的布局都要停止。不要清空界面编号，不要改本轮新响应 ID，不要把相同错误文案当作根因已经一致。

## 旧修复造成的位置错位

一个旧分段的文件比数据库游标所指长度短。原备份和旧事务清单证明，早期脚本删除了推理行并缩短编号，导致原字节位置和序号出现缺口。

恢复依据必须同时包括：当前文件精确匹配旧事务输出、原备份哈希与长度、逐行可解释差异、数据库原边界及现行语义检查。由原布局构造新副本，先备份本次操作前状态，再用已验证的等长非模型占位保留不可用项的位置。后来追加过内容或任一证据缺失就停止；不能猜测补空白、按当前行号重排或无条件覆盖旧备份。

同轮还验证了空界面投影和复制父继承元数据的物化分支。它们不是一律损坏，也不是一律可写；要核对归属、游标、轮次引用和完整压缩基线，并用原生副本读取与追加索引证明。

## 验证分层，不能混成一句“已修好”

- **真实请求副本**：正式代码修复的故障副本通过官方预热和续传；禁用工具执行，不向原任务发消息。
- **完整离线副本**：415 个文件和 3 个相关数据库；392 个文件修复后逐行比较正文、工具、加密字段与界面记录，数据库哈希不变，全部文件精确回滚。副本不携带真实认证，测试后清理。
- **停机执行与重开核对**：用户退出所有写入者后执行，392 个修复文件的前缀哈希核对通过，重点文件正文与字节边界保留，三库完整性通过；当前会话续聊、压缩和新消息索引正常。
- **尚未覆盖**：不是全部旧任务、账号、供应商或平台的真实模型验收；新规则未证明旧式布局可直接迁移，也未完成历史修复强杀／断电后的自动恢复验收。

约 2.5 GB 副本的准备阶段约 313 秒，完整复制、比对与回滚演练约 359 秒。优化批量解析／写入和重复数据库查询后，仍保留原安全判断。首次批量准备和演练总时长不能宣传成日常切换速度；临时测试副本和用户需要的恢复材料也不是同一类文件。

## 给后续实现的结论

“修复失败就不切换”必须保留，但还应覆盖历史事务被中断后的再次启动：先发现未完成或回滚失败的清单，核对原状态、目标状态和未知状态，再决定恢复；无法安全判断就停止新操作。正常异常回滚和配置恢复不能证明历史断电恢复。事故记录时本机尚有此缺口，后续改造的范围与限度见开头更新，不随本仓库提供成品程序。

一键入口和少量模块可以保留，无需堆出通用 Codex 修复器。把已验证规则、正式写入器与一次性救援材料隔离，未知情况停住，不把网络超时、503 或模型满载自动归入历史清理。

实施前读[历史兼容](history-compatibility.md)、[安全与回滚](safety-and-rollback.md)和[验证清单](validation.md)，选择适合本机的方案；不要把本案例当成可直接执行的迁移命令。
